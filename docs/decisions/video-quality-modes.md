# 标准、清晰、动画画质模式

日期：2026-10-05。范围：Windows 内置 libmpv；外部 mpv 的配置和接管流程不变。

## 产品与契约

默认标准。正式播放器在倍速旁提供画质菜单，只有三个名称与当前项勾选；点击即关闭，确认渲染成功后更新选择。切换时只禁用画质入口，其余播放操作可用。不提供说明副文案、按住对比、强度、算法选择、自动性能降级或第四种模式。

播放器手动成功选择后按账号作用域和整剧 ID 保存；没有整剧 ID 时按条目 ID 保存，电影按条目保存。没有内容偏好的条目使用标准。**不提供全局默认画质**：新功能的控制只放在功能自己的界面里，设置页不出现画质项；早期版本写过的 `DefaultVideoQualityMode` 字段读取时忽略，下次保存后消失。

公开边界为 `VideoQualityMode`、`IPlaybackSession.SetVideoQualityModeAsync` 和快照的已应用模式、切换中状态、独立画质错误。界面不接触算法、路径或 Player 内部类型。Demo、延迟会话包装、真实会话均支持相同契约。

`SettingsStore` 在现有文档内增加独立 `VideoQualityPreferences` 字典，复用原子合并写入和 JSON 源生成。键使用已有账号作用域 SHA-256 加 `|series|ID` 或 `|item|ID`；不写入服务器地址或凭据。缺字段采用标准/空字典；错误类型、未知枚举和损坏条目局部修复，其他设置保留。偏好与音量、主题、弹幕等更新经过同一写入串行器。整份设置文档每次保存（包括调音量）都会重写，所以偏好只保留最近选择过的 500 项：再次选择会把该项排到最新，超出时丢弃最早的，读取更长的旧字典时同样截断。

## 固定配方

| 模式 | scale | scale-antiring | 着色器处理 |
|---|---|---|---|
| 标准 | lanczos | 0 | 无，清空着色器 |
| 清晰 | ewa_lanczossharp | 0.6 | CAS FP32 sharpen-only，sharpness 0，35% 增强混合；放大和等大时在 MAIN，缩小时在 SCALED |
| 动画 | ewa_lanczossharp | 0.6 | Anime4K B Fast 与 Mambo HDR 包装 |

三者固定 `dscale=hermite`、色度缩放继承，不加载 `high-quality` profile，不改现有色调映射、HDR 峰值或对比度策略。**锁定 mpv 的公开 `cscale` 继承值实际是空字符串**，计划中的 `inherit` 是语义而不是合法字面值。真实 D3D11 和 `vo=null` 属性测试均验证过；NODE 读取此枚举可能返回整数 0。

CAS 锁定 [AMD 官方提交 9fabcc9](https://github.com/GPUOpen-Effects/FidelityFX-CAS/tree/9fabcc9a2c45f958aff55ddfda337e74ef894b7f)。源空间接入在 MAIN 使用 `linearize`，按 `P=max(1,max(linearize(vec4(1)).rgb))` 归一化。邻域含非有限、负值或超范围信号时保留中心像素；正常像素运行 CAS，再反归一化、混合、`delinearize`，保留 alpha。sharpness=0 不是关闭锐化。此位置不同于 AMD 建议的色调映射后位置，不能用 SDR 编译结果代替 HDR→SDR 观感验收。

清晰每帧只运行两个 pass 之一，条件互补：输出面积不小于片源面积（放大、等大）时运行上述 MAIN 源空间 pass；输出面积小于片源（缩小）时改为运行 SCALED 上的 pass。libplacebo 在线性光下缩小，此时 SCALED 已经是源空间 pass 用 `linearize` 得到的同一种线性 RGB，所以缩放后的 pass 不施加任何传递函数；归一化、有效性判定和核由两个 pass 共用（`adapters/cas.glsl`）。等大时 SCALED 仍是编码值，因此等大归入源空间 pass。

选择这种分法的依据是实测，不是推断。RTX 4060 Laptop 上取窗口截图与标准模式的 RMS 差（数值越大锐化越明显）：

| 情形 | 源空间（MAIN） | 缩放后（SCALED） |
|---|---|---|
| 2 倍缩小，mandelbrot / testsrc2 | 0.0009 / 0.0005 | 0.0030 / 0.0020 |
| 1.33 倍缩小 | 0.0013 / 0.0008 | 0.0027 / 0.0019 |
| 等大 | 0.0033 / 0.0017 | — |
| 2.5 倍放大 | 0.0026 / 0.0014 | 0.0012 / 0.0011 |

先锐化再缩小时，1 像素尺度的增强大半被缩小滤掉，2 倍缩小只剩约三成；先放大再锐化则反过来，只剩不到一半。因此不把清晰整体挪到缩放之后。两个 pass 都在色调映射之前。

Anime4K 锁定 [v4.0.1 / 4029bf7](https://github.com/bloc97/Anime4K/tree/4029bf701ecaa15f163cdc49cffe5501c1acf410)，顺序为 Clamp_Highlights、Restore_CNN_Soft_M、Upscale_CNN_x2_M、AutoDownscalePre_x2、AutoDownscalePre_x4、Upscale_CNN_x2_S。保留各级原有 WHEN 尺寸条件和 OFFSET 像素对齐；窗口变化由渲染条件决定，不由宿主反复加载预设。等大/缩小时跳过超分属于正常执行，Restore 等可适用步骤仍保留。

HDR 包装是 **Mambo 自定义处理，并非 Anime4K 官方原生 HDR**：

- 在着色器内以 `P>1.01` 选择 HDR 分支，SDR 沿用原处理。来源是当前帧的传递函数，不用异步元数据切换链。
- 保存源编码图、线性 RGB 和未处理代理基线。线性 maxRGB 为 m，代理为 `(m/(1+m))^(1/2.2)`；Anime4K 处理灰度代理。
- 基线与原图跟随各级放大/缩小更新坐标和偏移，避免将不同插值路径误判为增强。逆代理比值形成统一 RGB 增益，限定 0.90–1.10；局部平坦区域关闭，近黑保留，名义信号上限处限制新增增益。
- HDR 代理末尾在 MAIN 裁剪后重建；官方 PREKERNEL Clamp 的 HDR 分支直通，SDR 分支保留。恢复源传递函数和 alpha 后交回既有 mpv 色彩管理。

源图也跟随 Anime4K 中间尺寸重采样，因此不承诺动画模式与标准模式的缩放基线逐像素相同。代理往返数学测试不等于全管线图像无误差。

## 应用、确认与失败恢复

`VideoQualityController` 独占预设拥有的六个属性。三种模式取值相同的 `dscale`、`cscale`、`glsl-shader-opts` 每个引擎只写一次；切换只写 `scale`、`scale-antiring` 和 `glsl-shaders`，着色器列表整体替换、不经过空列表，清晰与动画互切不会漏出一帧标准画面。已经完整写入的预设不重写：加载前准备好的模式、换集沿用的模式，首帧就带着效果。通过 NODE 数组设置 `glsl-shaders`，不用含分隔符的拼接字符串。所有安装资源先与程序集嵌入副本计算 SHA-256 对比；副本随 AOT 编译保留，不能只靠可被一同修改的旁置 manifest 信任文件。

首次非追加加载前准备资源和配方。追加预加载不改变当前画质；实际 START_FILE 选择条目，FILE_LOADED 后确认适用模式。重试和重建重新解析同一内容偏好。等待渲染在会话消息循环之外运行；会话、引擎、条目、请求版本共同防止过期结果覆盖当前状态。取消后先撤销半套参数，再让下一请求写入。

属性设置成功不视为着色器执行成功。控制器在写入着色器列表前记下 `vo-passes` 与失败计数，之后才出现的帧和失败才属于这套预设；区分 fresh/redraw 的变化，等待对应模式的 pass 真正执行，且同一组里没有另一模式的 pass。同一预设不重写，所以不存在需要先回到标准才能排除的同名残留。20 秒的确认期限从写入之后的第一帧算起：起播慢、缓冲和首次着色器编译期间没有新帧，不计入期限，也不再因此误报失败。没有视频轨的条目不等待确认。条件未触发的超分 pass 不作为错误。真实编译失败仅转换为安全错误类别和计数；不保留或转发 mpv 原始日志、媒体地址或着色器日志正文。可恢复缓存警告不误判为编译失败。

确认之后引擎继续监听着色器失败；日志只订阅错误级别，来源在原生字节上筛选。已确认的增强之后才失效时（例如窗口放大后才第一次编译的超分 pass、窗口缩小后才编译的清晰缩放后 pass），控制器清除增强并发出 `EngineEvent.VideoQualityLost`；会话经同一条串行切换通道回到标准，给出非致命提示 `player.video_quality_lost`，已保存的偏好不变。

手动失败恢复上一个成功预设并确认其渲染；历史自动恢复失败显式确认标准，保留历史偏好并提示。上一个资源也损坏时清除增强，返回专用安全错误码，让勾选与实际标准一致。关闭/切集取消不等待已不存在的旧帧；恢复任务均有时间上限。错误回退是故障处理，不是性能降级。

据此的结论：

- 首次启用某模式要编译着色器，按片源与显示尺寸的组合各一次，本机 2.5–6.5 秒，期间画面不更新；缓存之后切换约 0.2–0.3 秒。缓存在 `%LOCALAPPDATA%\Mambo\mpv\shader-cache`，显卡驱动更新后会重新编译。没有做预热。
- 24 fps 的帧预算是 41.7 ms，三种模式在本机都不丢帧。清晰的开销几乎全在 `ewa_lanczossharp` 与抗振铃，CAS 本身只有 0.15–0.7 ms；1080p → 1440p 时清晰的每帧耗时高于动画。弱显卡上清晰同样可能吃紧，配方未改。
- 动画的 HDR 包装在 SDR 片源上占该模式 GPU 时间的 8–16%，即 0.7–2.0 ms。没有拆成 SDR 和 HDR 两份着色器：拆分要靠异步元数据在换集时切换整条链，正是本设计刻意避免的，而这部分开销在本机不影响流畅度。
- HDR 片源在动画模式下放大时，原图跟随 Anime4K 的中间尺寸做双线性重采样，网络只贡献 ±10% 增益，边缘可能比标准模式软。未改，留作 HDR 人工验收的观察项。
- 未测：专用显存、AMD 和 Intel 显卡、真实片源解码叠加后的掉帧。

## 【需用户】人工验收与未测范围

代码和自动检查不代替 AGENTS.md 规定的真实显示效果验收。以下状态保持未验收，不推断 RTX 4060 的结果代表其他硬件：

- SDR→SDR/HDR、PQ/HLG→HDR/SDR 的灰阶、纯色、肤色、高光、暗部、alpha 和无增强往返图像；Windows HDR 开关及跨显示器变化。
- 新番、老动画、颗粒动画电影、真人片源的白边、纹理损失、闪烁和色偏，特别是源空间 CAS 的 HDR→SDR 接入。
- 不同大小窗口及全屏的实际观感，暂停与连续运动；NVIDIA/AMD/Intel 可获得机器分别记录。
- 清晰在缩小播放时的观感，例如 4K 片源在 1440p 屏幕或小窗口：修订后这一情形的锐化明显强于修订前。
